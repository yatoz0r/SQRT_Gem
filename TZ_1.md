# Техническое задание на учебный проект

## 1. Общая информация о проекте

### 1.1. Назначение

Необходимо разработать программный продукт для выполнения математических вычислений по введённым пользователем числам и аналитическим выражениям.

Исходная учебная задача проекта — программа, вычисляющая корень из заданного числа. В рамках итогового проекта эта функциональность должна быть развита до полноценного прикладного программного продукта с графическим интерфейсом, поддержкой чисел произвольной длины, управляемой точностью вычислений и вывода, обработкой ошибок, тестированием, документацией, установкой, удалением, обновлением и сопровождением.

Проект должен рассматриваться не как набор исходных файлов, а как законченный программный продукт, предназначенный для передачи конечному пользователю.

### 1.2. Тип проекта

Учебный командный проект по разработке программного обеспечения.

В проекте должны быть отражены все основные этапы жизненного цикла ПО:

- анализ требований;
- проектирование;
- разработка;
- тестирование;
- сборка;
- деплой;
- установка;
- обновление;
- удаление;
- сопровождение;
- планирование дальнейшего развития.

---

# 2. Пользователи и область применения

Команда должна определить целевую аудиторию проекта и описать её в документации.

Минимально должны быть рассмотрены следующие группы пользователей:

1. обычный пользователь, которому необходимо выполнить расчёт;
2. технически подготовленный пользователь, которому важны высокая точность, воспроизводимость и расширенные возможности;
3. пользователь, устанавливающий, обновляющий или удаляющий программу;
4. техническая поддержка, ответственная за диагностику проблем.

Команда должна сформулировать не менее 3–5 пользовательских сценариев.

Примеры:

- вычисление квадратного корня из числа;
- вычисление выражения с несколькими операциями;
- вычисление результата с заданным количеством знаков после запятой;
- работа с очень длинным числом;
- сохранение и повторное выполнение выражения;
- изменение языка интерфейса;
- обновление приложения;
- полное удаление приложения.

# 3. Функциональные требования

## 3.1. Базовые вычисления

Программа должна поддерживать вычисление математических выражений.

Минимальный набор операций:

- сложение;
- вычитание;
- умножение;
- деление;
- возведение в степень;
- квадратный корень;
- изменение знака числа;
- использование круглых скобок.

Должна поддерживаться стандартная приоритетность математических операций.

Программа должна корректно обрабатывать как отдельные числа, так и составные выражения, например:

```text
sqrt(12345678901234567890)
```

```text
(15.5 + 2.75) * sqrt(144)
```

```text
123456789012345678901234567890 / 987654321
```

### 3.2. Числа произвольной длины

Обычные типы фиксированной разрядности, такие как `float32`, `float64` или аналогичные, не должны использоваться как единственный механизм хранения результата там, где это приводит к потере требуемой точности.

Должна быть обеспечена работа с числами, существенно превышающими диапазон стандартных машинных типов.

Минимальные требования:

- целые числа не менее 1000 десятичных цифр;
- десятичные числа не менее 1000 цифр в представлении;
- корректная работа с числами, имеющими большое количество знаков после запятой;
- отсутствие необоснованного перехода к типам ограниченной точности.

Использование готовых библиотек произвольной точности разрешается и рекомендуется.

### 3.3. Точность вычислений

Пользователь должен иметь возможность задавать требуемую точность результата.

Минимально необходимо поддержать диапазон:

```text
от 0 до 1000 знаков после десятичной точки
```

с возможностью расширения диапазона при наличии технической необходимости.

Необходимо определить:

- внутреннюю точность вычислений;
- точность отображения;
- правила округления;
- поведение при превышении максимально допустимой точности.

В документации должна быть явно описана разница между точностью хранения, точностью вычислений и точностью отображения результата.

Пример:

```text
Выражение:
sqrt(2)

Точность:
50 знаков

Результат:
1.414213562373095048801688724209698078569671875376948
```

Конкретный формат вывода должен быть выбран командой и описан в технической документации.

### 3.4. Аналитические выражения

Под аналитическими выражениями в рамках данного задания понимается возможность пользователя вводить полноценное математическое выражение, а не только одну операцию над двумя числами.

Минимально должны поддерживаться:

```text
+
-
*
/
^
()
sqrt()
```

Команда может добавить дополнительные функции:

```text
abs()
sin()
cos()
tan()
ln()
log()
exp()
```

и другие.

Если реализуются функции, зависящие от точности вычислений, правила их вычисления и ограничения также должны быть описаны в технической документации.

Символьные преобразования выражений в стиле систем компьютерной алгебры не являются обязательными.

### 3.5. История вычислений

Программа должна предоставлять пользователю возможность просматривать результаты последних вычислений.

Минимальный вариант:

- выражение;
- дата/время выполнения;
- использованная точность;
- полученный результат.

Способ хранения истории определяется командой.

### 3.6. Дополнительная функциональность

Команда может реализовать дополнительные возможности:

- сохранение выражений;
- экспорт результатов;
- импорт выражений;
- копирование результата;
- горячие клавиши;
- сохранение настроек;
- режим научной записи;
- комплексные числа;
- дополнительные математические функции.

Дополнительная функциональность не должна ухудшать выполнение обязательных требований.

# 4. Обработка ошибок и ошибкоустойчивость

Программа должна корректно обрабатывать некорректные действия пользователя и внутренние ошибки.

Минимально необходимо обработать:

- деление на ноль;
- извлечение квадратного корня из недопустимого значения;
- синтаксически некорректное выражение;
- неизвестную функцию;
- незакрытые скобки;
- переполнение доступных ресурсов;
- слишком большую заданную точность;
- повреждённые пользовательские настройки;
- недоступные файлы при операциях чтения/записи;
- ошибку обновления;
- некорректную конфигурацию.

Программа не должна завершаться аварийно при обычных ошибочных действиях пользователя.

Сообщения об ошибках должны:

1. быть понятными пользователю;
2. указывать причину ошибки;
3. по возможности содержать способ исправления;
4. не раскрывать внутреннюю техническую информацию, если она не предназначена для пользователя.

Для технической поддержки должна существовать возможность получения технической информации об ошибке.

---

# 5. Графический интерфейс

Программа должна иметь графический пользовательский интерфейс.

Выбор UI-фреймворка оставляется за командой.

Интерфейс должен обеспечивать:

- ввод выражения;
- отображение результата;
- изменение точности;
- изменение языка;
- отображение ошибок;
- просмотр истории;
- доступ к настройкам;
- запуск обновления либо отображение информации о доступных обновлениях.

Допускается свободный выбор дизайна.

При этом интерфейс должен быть согласованным: одинаковые действия должны одинаково выглядеть и работать во всех частях программы.

Должны быть предусмотрены как минимум базовые сценарии работы с клавиатурой и мышью.

---

# 6. Полиязычность

Программа должна поддерживать минимум четыре языка:

1. русский;
2. английский;
3. испанский;
4. китайский.

Перевод должен распространяться как минимум на:

- элементы интерфейса;
- сообщения об ошибках;
- настройки;
- пункты меню;
- документацию пользователя либо её соответствующую локализованную часть.

Переключение языка должно выполняться без необходимости переустановки программы.

Архитектура проекта должна позволять добавлять новые языки без переписывания логики приложения.

Запрещается реализовывать перевод отдельных строк исключительно через условные конструкции в бизнес-логике вида:

```text
if language == "ru" ...
else if language == "en" ...
```

Для локализации необходимо использовать отдельный механизм ресурсов.

---

# 7. Кроссплатформенность

Команда должна самостоятельно определить перечень официально поддерживаемых платформ.

Минимально необходимо обеспечить работу хотя бы на двух различных операционных системах.

Рекомендуемый вариант:

- Windows 10/11 x64;
- Linux x64 на одной из распространённых дистрибуций.

Поддержка macOS является дополнительным преимуществом.

В документации необходимо явно указать:

- поддерживаемые ОС;
- архитектуры процессоров;
- минимальные версии ОС;
- системные зависимости;
- ограничения конкретных платформ.

Фраза «программа кроссплатформенная» без конкретного списка поддерживаемых платформ считается недостаточной.

---

# 8. Переносимость и развёртывание

Необходимо предусмотреть возможность переноса приложения на другой компьютер.

Минимально должны существовать:

1. штатный способ установки;
2. вариант запуска из заранее подготовленного дистрибутива либо portable-пакета, если это технически возможно.

После копирования или установки приложения пользователь не должен вручную устанавливать десятки зависимостей и выполнять действия, описанные только для разработчиков.

Все необходимые зависимости должны:

- поставляться с приложением;
- либо устанавливаться автоматически;
- либо быть чётко указаны в системных требованиях.

---

# 9. Установка

Необходимо предоставить полноценный механизм установки программы.

Установка должна:

- выполняться воспроизводимо;
- не требовать ручного копирования файлов разработчиком;
- создавать необходимые конфигурации;
- создавать ярлыки либо другие предусмотренные способы запуска;
- корректно обрабатывать повторную установку;
- не ломать уже установленную рабочую версию.

Команда должна предоставить инструкцию по установке для конечного пользователя.

---

# 10. Удаление программы

Удаление программы должно быть максимально полным и предсказуемым.

После удаления не должны оставаться:

- исполняемые файлы приложения;
- библиотеки приложения;
- временные файлы;
- созданные приложением служебные файлы;
- записи конфигурации;
- элементы автозапуска;
- служебные записи, созданные установщиком.

Пользовательские данные, например история вычислений, должны обрабатываться согласно явно выбранной пользователем политике.

При удалении должна быть предусмотрена возможность выбора:

```text
Удалить программу, сохранив пользовательские данные
```

или

```text
Удалить программу вместе с пользовательскими данными
```

Под «полным удалением» понимается удаление всех артефактов, созданных приложением и заявленных разработчиками как удаляемые.

Наличие стандартных механизмов ОС, которые могут сохранять системные журналы или кэш операционной системы, не считается ошибкой приложения.

---

# 11. Обновление программы

Необходимо разработать политику обновлений.

Минимально должны быть определены:

- формат версии;
- схема нумерации версий;
- типы релизов;
- способ доставки обновлений;
- проверка наличия обновлений;
- совместимость версий;
- поведение при ошибке обновления;
- возможность отката при неудачном обновлении.

Команда должна описать хотя бы два типа обновлений:

```text
обычное функциональное обновление
```

и

```text
критическое исправление
```

Должно быть предусмотрено безопасное поведение в случае прерывания обновления.

Необходимо также описать стратегию долгосрочной поддержки версий.

---

# 12. Эксплуатация и поддержка

Проект должен предусматривать жизненный цикл программного продукта после выпуска первой версии.

Команда должна разработать правила поддержки.

Необходимо определить:

- каналы обращения пользователей;
- рабочие часы поддержки;
- категории инцидентов;
- приоритеты;
- предполагаемое время реакции;
- порядок регистрации обращения;
- порядок эскалации;
- правила выпуска исправлений;
- порядок закрытия обращения.

Например, команда может использовать классификацию:

```text
P1 — программа полностью не работает
P2 — критическая функция недоступна
P3 — существенная ошибка, существует обходной путь
P4 — некритическая ошибка или предложение по улучшению
```

Для каждой категории должны быть заданы правила обработки.

---

# 13. Специальное требование по снижению стоимости поддержки

Команда должна предложить минимум один нетривиальный механизм, уменьшающий объём ручной поддержки пользователей.

Идея должна быть не просто «написать хорошую документацию».

Необходимо показать, каким образом архитектура или функциональность продукта уменьшает количество обращений в техническую поддержку.

Направления, которые могут рассматриваться:

- диагностический режим;
- автоматическая проверка конфигурации;
- встроенное описание ошибок;
- автоматическое формирование диагностического отчёта;
- self-service восстановление;
- мастер исправления типовых проблем;
- автоматическая проверка окружения;
- база знаний внутри приложения;
- воспроизводимый сбор технической информации.

Требование является открытым: конкретное решение команда должна предложить, реализовать и экономически обосновать.

# 14. Документация

В проекте должны присутствовать как минимум следующие документы.

## 14.1. Руководство пользователя

Должно содержать:

- назначение программы;
- установку;
- первый запуск;
- основные операции;
- работу с точностью;
- изменение языка;
- работу с историей;
- обновление;
- удаление;
- решение типовых проблем.

## 14.2. Техническая документация

Должна описывать:

- архитектуру;
- основные компоненты;
- зависимости;
- формат данных;
- механизм вычислений;
- обработку ошибок;
- локализацию;
- систему сборки;
- тестирование;
- упаковку;
- обновление;
- удаление;
- ограничения системы.

## 14.3. Документация кода

Исходный код должен быть структурирован и документирован.

Документировать необходимо прежде всего:

- публичные интерфейсы;
- сложные алгоритмы;
- нетривиальные решения;
- важные ограничения;
- места, где выбранное решение не является очевидным.

Документация не должна состоять из комментариев, повторяющих очевидный код.

## 14.4. Документ проектирования

До начала реализации либо на раннем этапе разработки команда должна сформировать документ проектирования.

Минимально он должен содержать:

- цели;
- функциональные требования;
- нефункциональные требования;
- архитектуру;
- технологический стек;
- основные компоненты;
- модель взаимодействия компонентов;
- риски;
- ограничения;
- принятые архитектурные решения.

# 16. Тестирование

Требуется полноценная система тестирования, а не только набор unit-тестов.

## 16.1. Unit-тестирование

Должны быть покрыты как минимум:

- арифметические операции;
- вычисление корня;
- парсер выражений;
- работа с точностью;
- обработка ошибок;
- локализация;
- важные вспомогательные компоненты.

## 16.2. Интеграционное тестирование

Необходимо проверить взаимодействие компонентов:

- UI ↔ вычислительное ядро;
- настройки ↔ приложение;
- история ↔ файловая система;
- установка ↔ запуск;
- обновление ↔ старая версия.

## 16.3. End-to-end тестирование

Необходимо реализовать тесты пользовательских сценариев.

Например:

```text
установить приложение
→ запустить
→ выбрать язык
→ ввести выражение
→ задать точность
→ получить результат
→ сохранить результат
→ обновить приложение
→ удалить приложение
```

## 16.4. Чёрный ящик

Должны присутствовать тесты, в которых система проверяется только через внешний интерфейс, без знания внутренней реализации.

В качестве входов используются реальные пользовательские сценарии.

## 16.5. Белый ящик

Для критических компонентов должны применяться тесты, учитывающие структуру реализации.

Необходимо показать:

- какие ветви кода проверяются;
- какие условия проверяются;
- какие участки остаются непокрытыми.

## 16.6. Покрытие

Необходимо предоставить количественную информацию о покрытии тестами.

Минимальное требование:

```text
не менее 80% покрытия критического вычислительного ядра
```

Для остальных компонентов команда должна установить целевые показатели самостоятельно и обосновать их.

Само число покрытия не считается доказательством качества тестов: необходимо привести примеры тестируемых сценариев и объяснить выбранный подход.

# 17. Проверка точности вычислений

Отдельно необходимо проверить математическую корректность вычислений.

Для этого должны использоваться эталонные значения либо независимый механизм вычисления.

Необходимо проверить как минимум:

- малые числа;
- большие числа;
- очень большие числа;
- числа с большим количеством знаков после запятой;
- значения около нуля;
- пограничные значения;
- операции с различной требуемой точностью;
- ошибки округления;
- сложные составные выражения.

Особое внимание должно быть уделено вычислению квадратного корня, так как именно эта операция являлась исходной постановкой задачи.

# 18. Деплой

Проект должен иметь воспроизводимый процесс сборки и выпуска.

Необходимо обеспечить:

- сборку проекта с нуля;
- создание готового пакета;
- получение версии приложения;
- запуск тестов перед выпуском;
- формирование релизных артефактов.

Желательно автоматизировать процесс с помощью CI/CD.

Минимальная цепочка:

```text
commit
→ build
→ tests
→ package
→ release artifact
```

Ручное копирование файлов из среды разработки в релизный пакет не допускается.

# 29. Основная идея задания

В начале проекта студентам выдаётся простая программа, решающая задачу вычисления корня из числа.

Задача команды состоит не в том, чтобы просто увеличить количество строк кода.

Необходимо показать, как из небольшой технической функции создаётся законченный программный продукт:

```text
маленький алгоритм
        ↓
требования
        ↓
архитектура
        ↓
пользовательский интерфейс
        ↓
обработка ошибок
        ↓
тестирование
        ↓
сборка
        ↓
установка
        ↓
обновление
        ↓
удаление
        ↓
поддержка
        ↓
планирование
        ↓
стоимость владения
        ↓
жизненный цикл продукта
```

Основным объектом оценки является не только правильность математического результата, но и способность команды спроектировать, реализовать, проверить, выпустить и сопровождать программный продукт на всём протяжении его жизненного цикла.
