## 1. Стиль исходного кода и правила именования

Проект строго следует стандарту **PEP 8** и принципам **Clean Code**:
- **Именование:**
  - Модули и пакеты: `snake_case` (например, `decimal_math.py`, `health_checker.py`).
  - Классы и исключения: `PascalCase` (например, `MathEngine`, `DivisionByZeroError`).
  - Функции и методы: `snake_case` (например, `evaluate()`, `get_app_data_dir()`).
  - Константы: `UPPER_SNAKE_CASE` (например, `MAX_SUPPORTED_PRECISION`, `GUARD_DIGITS`).
- **Форматирование:**
  - Длина строки: не более 120 символов.
  - Обязательная явная типизация параметров и возвращаемых значений (`typing` / Type Hints).
  - Комментарии и докстринги оформляются согласно PEP 257 на английском языке для публичных интерфейсов и алгоритмических нетривиальных мест.

## 3. Регламент работы с Git: ветвление и коммиты

### 3.1. Стратегия ветвления (Git Flow):
- `main`: стабильный производственный код, только релизные тэги (`v1.0.0`, `v1.1.0`).
- `develop`: основная ветка интеграции разрабатываемых фичей.
- `feature/<название-фичи>`: ветка разработки конкретной задачи от `develop`.
- `hotfix/<название-хотфикса>`: ветка срочного исправления дефекта от `main`.

### 3.2. Формат коммитов (Conventional Commits):
Сообщения коммитов формируются по шаблону: `<тип>(<область>): <краткое описание>`

**Допустимые типы:**
- `feat`: новая функциональность (например, `feat(engine): add ln and exp arbitrary precision functions`).
- `fix`: исправление ошибки (например, `fix(parser): handle consecutive unary minuses`).
- `test`: добавление или актуализация тестов (например, `test(core): add 1000-digit sqrt verification test`).
- `docs`: обновление документации (например, `docs(manual): update installation section`).
- `refactor`: изменение структуры кода без изменения функционального поведения.
- `ci`: настройка пайплайнов и скриптов сборки.

---

## 4. Правила Code Review и выпуска релизов

1. Ни один коммит не попадает в ветки `main` или `develop` напрямую без Pull Request / Merge Request.
2. Для слияния PR требуется:
   - Минимум один успешный approve от профильного разработчика (Core или UI).
   - 100% успешное прохождение всех автоматических тестов в CI.
   - Отсутствие снижения метрики тестового покрытия (для ядра строго $\ge 80\%$).
3. Выпуск релиза сопровождается обновлением версии в `src/__init__.py`, формированием релизного тэга `git tag -a vX.Y.Z` и генерацией ChangeLog.
